# i18n - usage

Within `src/utils/i18n.ts`, you will find some boilerplate code provided for you which will activate [your app's locale configuration](/docs/utils/i18n/config). This code uses a util provided by Psychic to provision a curried `i18n` function for you, which will carefully absorb the locale shape of your config and use it to provide type completion that will make your life much easier.

```ts
// src/utils/i18n.ts

import locales from '#conf/locales/index.js'
import { I18nProvider } from '@rvoh/psychic/system'
import { LocalesEnumValues } from '#src/types/db.js'

export function supportedLocales() {
  return LocalesEnumValues
}

export const DEFAULT_LOCALE: ReturnType<typeof supportedLocales>[number] = 'en-US'

export const BASE_LOCALE = 'en'

export default I18nProvider.provide(locales, BASE_LOCALE)
```

When calling `I18nProvider.provide`, the first argument will be the entire payload of locales from your application config, and the second argument, `BASE_LOCALE`, names the locale you are treating as your base locale. Its file's shape provides type completion as you use the i18n helper — `i18n()` only accepts dotted keys that exist in that base locale file, so pass the most complete one. At call time, the locale you pass is matched to a locale file by its language prefix (`'en-US'` matches the `en` locale file). An unmatched locale, or a key missing from the matched file, falls back to the base locale's text; a key missing there too returns the dotted key itself. To catch those gaps before a user sees them, see [catch missing translations in a spec](/docs/utils/i18n/config#catch-missing-translations-in-a-spec).

```ts
// elsewhere, in your app

const text = i18n('en-US', 'labels.nutrition.calories')
```

We recommend that you leverage i18n within your serializer layer, since this can be an incredibly convenient place to make translations before delivering your endpoint results.

See the [passthrough setting documentation](/docs/serializers/render#serializer-passthrough-data) for details on how to set passthrough data on automatically rendered serializers.

```ts
import { DreamSerializer } from '@rvoh/dream'
import { LocalesEnum } from '#src/types/db.js'
import i18n from '#src/utils/i18n.js'

export const PlaceForGuestsSerializer = (place: Place, passthrough: { locale: LocalesEnum }) =>
  PlaceSummaryForGuestsSerializer(place)
    .customAttribute('style', () => i18n(passthrough.locale, `places.style.${place.style}`), {
      openapi: 'string',
    })
    .attribute('sleeps')
    .rendersMany('rooms', { serializerKey: 'forGuests' })
```

This is **code-driven** i18n: translating static values — enum labels, UI strings — that come from your code, not from a user. Treat any user-facing label baked into an enum (a place style, a room type, a status) as an i18n concern from the start, with an entry in your locale files, rather than reaching for an ad hoc `Record<EnumValue, string>` lookup map next to the enum. A hand-rolled label map duplicates what `i18n()` already gives you — locale coverage, type-checked keys, and one lookup path for both static and user-generated content — and it silently stops working the moment you add a second locale. For translating user-generated content (a place's title, a listing's description), see [passthrough](/docs/models/querying/passthrough) for the `LocalizedText` pattern, which is the data-driven counterpart to this page.

## Passing locale from controllers

The generated `ApplicationController` reads the `Accept-Language` header with a `locale` getter. It lets Koa's `ctx.acceptsLanguages` pick the supported locale the header prefers — weighing q-values and matching a bare `es` to `es-ES` — and falls back to `DEFAULT_LOCALE` when the header is missing or accepts none of them:

```ts
// app/controllers/ApplicationController.ts

export default class ApplicationController extends PsychicController {
  protected get locale() {
    // Koa answers a missing or `*` header with the first locale it is given,
    // so DEFAULT_LOCALE goes first
    const locales = [DEFAULT_LOCALE, ...supportedLocales().filter(locale => locale !== DEFAULT_LOCALE)]
    return (this.ctx.acceptsLanguages(...locales) || DEFAULT_LOCALE) as (typeof locales)[number]
  }
}
```

Pass it to `serializerPassthrough` in a base controller, so every serializer rendered beneath it receives the locale:

```ts
// app/controllers/AuthedController.ts

export default class AuthedController extends ApplicationController {
  @BeforeAction()
  public configureSerializers() {
    this.serializerPassthrough({ locale: this.locale })
  }
}
```

When querying models that use passthrough-conditioned associations (like `currentLocalizedText`), pass the same resolved locale on the query, in addition to `serializerPassthrough`:

```ts
const places = await Place
  .passthrough({ locale: this.locale })
  .preloadFor('forGuests')
  .all()
```

`serializerPassthrough` and `.passthrough(...)` are two separate channels that happen to want the same value here — the former feeds serializer callbacks like `customAttribute`, the latter satisfies `and: { locale: DreamConst.passthrough }` conditions on associations. See [passthrough](/docs/models/querying/passthrough) for the association side of this pattern, including how to pair it with a fixed-locale fallback association.

## Output encoding

`I18nProvider` interpolation does not HTML-escape values. Psychic is a JSON API, so encode output in the frontend context that renders it. See [output encoding](/docs/security/output-encoding).
